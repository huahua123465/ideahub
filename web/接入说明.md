# IdeaHub 接入说明（给技术1 / 技术2）

对应《技术3｜IdeaHub团队资料库｜第一版任务表》的任务 10、11。

- 服务地址：`https://xm.xingxingqule.com:9443`
- 认证：请求头 `Authorization: Bearer <你的 api key>`
- 请求体：`application/json`，UTF-8
- 密钥由 IdeaHub 管理员在「团队 → 标签与对接」页生成，**只显示一次**，丢了就重新生成一把、把旧的停用。
  技术1 的钥匙写不了客户档案，技术2 的钥匙也写不了灵感 —— 权限是分开的。

先自测通不通：

```bash
curl -H "Authorization: Bearer $KEY" https://xm.xingxingqule.com:9443/api/ingest/ping
# {"ok":true,"name":"技术1","scopes":["tech1"]}
```

## 一、技术2：客户资料与 AI 分析

### `POST /api/ingest/client`

**同一个客户不会重复建档** —— 靠 `externalId` 认人，这是唯一必填项。
第一次调是建档，之后每次调都是更新同一条。

```json
{
  "externalId": "t2-8891",
  "alias": "L小姐",
  "tier": "A",
  "stage": "consulted",
  "female":   { "年龄": "29", "城市": "杭州", "职业": "设计师" },
  "male":     { "年龄": "33", "职业": "工程师" },
  "relation": { "关系阶段": "冷淡期", "见面次数": "6" },
  "timeline": "认识→升温→冷淡→现在",
  "aiSituation": "关系处于冷淡期，男方回避型依恋特征明显…",
  "aiUser": "用户焦虑型依恋，急于确认关系…",
  "deal": { "成交产品": "陪跑90天", "成交金额": "39800" },
  "tags": ["冷淡期", "判断对方态度"]
}
```

| 字段 | 说明 |
|---|---|
| `externalId` | **必填**。你那边的客户 id。同一个值永远对应 IdeaHub 里的同一条客户 |
| `alias` | 化名。**不要传真名**，IdeaHub 里全部是脱敏的 |
| `tier` | `S` / `A` / `B` / `C` |
| `stage` | `lead` 新客资 / `wechat` 已加微 / `profiled` 已建档 / `consulted` 已咨询 / `coaching` 已陪跑 / `renewed` 已续费 / `lost` 已流失 |
| `aiSituation` | AI **情况**分析。在客户详情页第⑤区单独显示 |
| `aiUser` | AI **用户**分析。第⑥区单独显示。两者必须分开传，不要合成一段 |
| `female` / `male` / `relation` / `deal` | 自由键值对，会和已有内容合并，不会互相覆盖 |
| `tags` | 标签**名字**数组。名字必须在 IdeaHub 的标签字典里，不在的会被忽略 —— 这是「全站统一标签」的前提，不接受随手造的新标签。要加标签请让管理员在界面上加 |

**没传的字段不会被清空**，业务人员在界面上手改过的等级、阶段、化名也不会被你的推送冲掉。

返回：`{"ok":true,"id":74,"created":false}` —— `created` 为 `false` 表示这次是更新已有客户。

### `POST /api/ingest/client/delivery`

追加一条交付记录（显示在客户详情页第⑧区）。

```json
{ "externalId": "t2-8891", "happenedAt": "2026-08-24", "kind": "陪跑", "summary": "第三周复盘" }
```

## 二、技术1：市场分析结果

### `POST /api/ingest/save`

业务人员在技术1 的结果页点「保存到 IdeaHub」时调这个口，**`type` 由他点了哪个按钮决定，后端不猜**。

| `type` | 存到哪 | 什么时候用 |
|---|---|---|
| `demand` | 用户需求 | 从评论/私信里提炼出的一条用户需求 |
| `idea` | **灵感池**（不是正式库） | 一个选题想法、一个可以做的方向 |
| `reference` | 对标作品台账 | 分析过的别人家的视频，指标一起带过来（**只有标题和几个指标**；要把完整分析推进来用下面的 `/api/ingest/analysis`） |

> **不会自动进正式库。** 正式库仍然只能由业务人员在 IdeaHub 里确认转入 —— 这是任务表写死的规则。

```json
{
  "type": "demand",
  "sourceRef": "t1-vid-5521",
  "sourceUrl": "https://v.douyin.com/xxxx",
  "title": "想让对方主动联系自己",
  "quote": "评论区高频：为什么我不主动他就不找我",
  "scene": "暧昧期停滞",
  "realGoal": "确认对方是否有意愿",
  "tags": ["暧昧期", "推进不动"]
}
```

`type: "idea"` 时用 `title` + `content`；`type: "reference"` 时用 `title` + `channel`（`persona`/`matrix`/`live`，默认 `matrix`）+ `metrics`（如 `{"曝光":220000,"收藏":8100}`）+ `publishedAt`。

| 字段 | 说明 |
|---|---|
| `sourceRef` | **必填**。你那边这条分析结果的 id。**同一个值重复保存不会产生第二条记录**，只会更新原来那条 |
| `sourceUrl` | 原视频 / 原评论的地址。IdeaHub 里每条资料都会显示「来源」，点得开原始出处 |
| `tags` | 同上，只认字典里已有的标签名 |

返回：`{"ok":true,"type":"demand","id":2,"created":true,"board":"demands"}`

### `POST /api/ingest/analysis?channel=persona`

**技术1 的采集分析结果，整份 JSON 原样 POST 进来就行** —— 不用拆字段、不用转 CSV、
不用改导出格式。它会落进「真人作品 / 矩阵作品」的**对标账号**里，
业务人员在 IdeaHub 里点开就能看到封面、账号粉丝数、公开互动数、AI 的视频七问和评论五问、
高赞评论原文、带时间码的完整逐字稿。

```bash
curl -X POST "https://xm.xingxingqule.com:9443/api/ingest/analysis?channel=persona" \
     -H "Authorization: Bearer $KEY" \
     -H "Content-Type: application/json; charset=utf-8" \
     --data-binary @女孩子无聊的本质是生命力的匮乏.json
```

用推送脚本更省事（一次一个文件夹）：

```bash
export IDEAHUB_KEY=ih_tech1_你的密钥
python3 推送到ideahub.py analysis persona 今天跑出来的结果/
```

**`channel` 决定进哪个板块**，写在 URL 上（JSON 里一个字都不用动）：

| `channel` | 落到哪 |
|---|---|
| `persona` | 真人作品 → 对标账号 |
| `matrix` | 矩阵作品 → 对标账号 |
| `live` | 真人直播 → 对标直播 |
| `persona,matrix` | 同时进两个板块（同一个视频既是真人对标也是矩阵对标时用） |

不带 `channel` 默认 `matrix`。也可以在 JSON 顶层写 `"channel": "persona"`，URL 参数优先。

**JSON 里这些字段会被读出来**（其余字段一个不丢，原样存着，将来界面上要显示随时能取）：

| JSON 字段 | 用途 |
|---|---|
| `task_id` | **幂等依据**。同一个 task_id 推一万次也只有一条记录，放心重试。没有它就退回用 `source_url` 算指纹 |
| `title` / `post_title` / `display_title` / `cover_title` | 作品标题，按这个顺序取第一个非空的。`cover_title` 是封面 OCR、带识别误差，所以放最后 |
| `source_url` | 原作品链接，界面上「打开原作品」用 |
| `platform` | `xiaohongshu` / `douyin` / `kuaishou` / `weibo` / `bilibili` / `wechat`，认不出来算「其他」 |
| `account.*` | **对标账号台账会自动建档**：账号名、主页、粉丝数、简介。粉丝数每次推送都刷新 |
| `engagement.likes/collects/comments` | 「4万」「3.2万」这种缩写会被读成数字（40000 / 32000），能排序能筛选 |
| `topics` | 当标签名来认，**只认 IdeaHub 标签字典里已有的**，其余忽略 |
| `ai_analysis.video.items.main_topic.summary` | 写进台账的「备注」，这样只看表格的人也知道这条讲什么 |
| `media_assets.video.cover_image_b64` | **封面原图，强烈建议给这个**。见下面「关于封面清晰度」 |
| `media_assets.video.*` | 封面地址、时长、尺寸、清晰度 |
| `video_text` + `video_text_meta` | 逐字稿。有段没识别成功（`chunks_succeeded < chunks_total`）界面上会标出来 |
| `comments` / `comment_summary` | 高赞评论原文 + 「扫了多少条」这些说明 |
| `ai_analysis.*.items` | 视频七问和评论五问，连 `evidence_comments` 里的原话一起显示 |
| `schema_version` | 记下来。以后格式换代了两边对得上 |

返回：

```json
{"ok":true,"taskId":"f90d29b0a27b","title":"女孩子无聊的本质是生命力的匮乏",
 "id":41,"created":true,
 "results":[{"channel":"persona","board":"persona","id":41,"created":true,
             "accountId":9,"tagsApplied":2}]}
```

#### 关于封面清晰度（请务必看一眼）

平台给的 `thumbnail_url` 是 **CDN 的预览变体**（小红书那份是 `!nd_prv_wlteh_jpg_3`）：
尺寸写着 1080×1441，实际只有 **27KB**，每像素 0.017 字节 —— 人脸糊成一片。
而且那个签名**只对这一个变体有效**，换成原图或其他清晰度后缀一律 403，
所以 IdeaHub 这边无论怎么处理都救不回来。

**解决办法：把整张封面直接放进 JSON。** 你那边为了做封面 OCR 本来就截过原始帧，给出来是顺手的事：

```json
"media_assets": {
  "video": {
    "cover_image_b64": "data:image/jpeg;base64,/9j/4AAQSkZJRg...",
    "thumbnail_url": "http://sns-webpic-qc.xhscdn.com/...",
    "duration_seconds": 296.077
  }
}
```

| 说明 | |
|---|---|
| 写法 | `data:image/jpeg;base64,xxx` 和光秃秃的 base64 都收，不用纠结 |
| 格式 | JPEG / PNG / WebP / GIF / AVIF。**按真实字节认，不看你声明的 mime** |
| 大小 | 单张上限 3MB。一张 1080×1920 的清晰竖图约 200~500KB，正常 |
| 请求体上限 | 这个接口放宽到 **8MB**（其他接口仍是 1MB） |
| 没给怎么办 | 自动退回去下 `thumbnail_url`，行为和以前完全一样，**不给也不会报错** |
| 存哪 | 收到就落成本地文件，之后一律走 `GET /api/works/:id/cover`，不受签名过期影响 |
| 会不会撑爆库 | 不会。图落地之后会从存档的 JSON 里摘掉，只留一句说明，其余字段一个不动 |

返回的 `results[]` 里没有封面字段，想确认用没用上你那张图，看 IdeaHub 界面上封面清不清楚即可
（或者问管理员看一眼 `digest.coverFrom`：`inline` = 用了你给的整张图，`url` = 退回去下的缩略图）。

**几条要知道的：**

1. **不覆盖人写的东西。** 台账里的「备注 / 复盘」一栏，业务人员写过就不会被你的推送冲掉
   （空着才填 AI 的一句话主题）。账号的「定位」同理。
   标题、链接、互动数这些客观事实每次推送都会刷新。
2. **被删过又推过来 = 这条对标回来了**，会自动恢复。
3. **请求体上限 1MB。** 一份带完整逐字稿和评论的分析大约 30KB，正常用不到上限；
   真超了会收到 400，把 `comments` 截短一点再推。
4. 这个口子只写**对标**（`side=benchmark`），永远不会动「自己账号」那半边。

## 三、错误码

| 状态 | 含义 |
|---|---|
| 401 | 没带 `Authorization` 头，或 key 无效 / 已停用 |
| 403 | key 的权限不对（技术1 的钥匙去调技术2 的口） |
| 400 | 必填字段缺失或取值不合法，`error` 字段里写了具体是哪个 |

---

## 四、给对接方的三条提醒

1. **`externalId` / `sourceRef` 一旦定下来就别改。** 它们是「同一条东西」的唯一依据，改了就会在 IdeaHub 里多出一条重复记录。
2. **标签只能用字典里已有的。** 需要新标签就找 IdeaHub 管理员在「标签与对接」页加一个，全站立刻可用。这是为了让「分手」在灵感、需求、案例、客户档案里是同一个词。
3. **失败要重试。** 接口是幂等的，同一条重复推送不会产生副本，放心重试。
