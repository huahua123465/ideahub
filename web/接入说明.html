IdeaHub · 对外接入

IdeaHub 接入说明

给技术1 和技术2 的写入接口。两条铁律贯穿全文：同一个客户不会被重复建档， 分析结果不会自动进正式库。照着填就行，接口是幂等的，失败可以放心重试。

服务地址 https://xm.xingxingqule.com:9443 认证 Authorization: Bearer <api key> 请求体 application/json · UTF-8
目录
接入方式 拿到钥匙 一、技术2 客户资料与 AI 分析 交付记录 二、技术1 市场分析结果 三、错误码 四、三条提醒

接入方式

你的系统保持独立：代码、服务器、数据库都还是你自己的。 你不需要 IdeaHub 的数据库账号、密码或端口 —— 两边唯一的接触点是一个 HTTPS 请求。

三步接完

1
拿一把密钥

找 IdeaHub 管理员要。他在「团队 → 标签与对接」页点一下生成，把那串 ih_tech1_… 或 ih_tech2_… 发给你。只显示一次，收到后请自己存好。

2
在你的代码里加一段 HTTP 请求

你的分析流程跑完、拿到结果的那一步之后，把结果按下面的字段拼成 JSON，POST 过去。用什么语言、什么 HTTP 库都行。

3
先 ping，再发一条真的

先调 /api/ingest/ping 确认密钥通了，再推一条真实数据。推完让 IdeaHub 那边在界面上确认能看到，就算接完了。

代码长这样

# Python
import requests

IDEAHUB = "https://xm.xingxingqule.com:9443"
KEY     = "ih_tech2_你的密钥"

def 推送客户(结果):
    r = requests.post(
        f"{IDEAHUB}/api/ingest/client",
        headers={"Authorization": f"Bearer {KEY}"},
        json={
            "externalId": 结果["客户id"],      # 你自己系统里的 id，别改
            "alias": 结果["化名"],
            "aiSituation": 结果["情况分析"],
            "aiUser": 结果["用户分析"],
        },
        timeout=10,
    )
    r.raise_for_status()
    return r.json()   # {"ok": true, "id": 74, "created": false}
// Node.js —— 不需要装任何依赖
const res = await fetch("https://xm.xingxingqule.com:9443/api/ingest/save", {
  method: "POST",
  headers: {
    "Authorization": `Bearer ${KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    type: "demand",
    sourceRef: 分析结果.id,          // 你自己系统里的 id，别改
    sourceUrl: 分析结果.视频链接,
    title: 分析结果.需求名称,
  }),
});
if (!res.ok) throw new Error(await res.text());

没有实时性要求。你可以跑完一条推一条，也可以攒一批定时推，还可以每天全量重推一遍 —— 接口按 externalId / sourceRef 判重，重复推送只会更新原来那条，不会产生副本。

拿到钥匙之后

密钥由 IdeaHub 管理员在「团队 → 标签与对接」页生成，只显示一次。 丢了就重新生成一把、把旧的停用。权限是分开的：技术1 的钥匙写不了客户档案，技术2 的钥匙也写不了灵感。

先自测通不通

# 不写任何数据，只验证钥匙
curl -H "Authorization: Bearer $KEY" \
     https://xm.xingxingqule.com:9443/api/ingest/ping

# {"ok":true,"name":"技术1","scopes":["tech1"]}

一、客户资料与 AI 分析 技术2

IdeaHub 负责长期保存和查看，技术2 负责收集和分析。同一个客户不要重复建档 —— 靠 externalId 认人，这是唯一必填项。

POST /api/ingest/client 第一次调是建档，之后每次调都是更新同一条 
{
  "externalId": "t2-8891",
  "alias": "L小姐",
  "tier": "A",
  "stage": "consulted",
  "female":   { "年龄": "29", "城市": "杭州", "职业": "设计师" },
  "male":     { "年龄": "33", "职业": "工程师" },
  "relation": { "关系阶段": "冷淡期", "见面次数": "6" },
  "timeline": "认识→升温→冷淡→现在",
  "aiSituation": "关系处于冷淡期，男方回避型依恋特征明显…",
  "aiUser": "用户焦虑型依恋，急于确认关系…",
  "deal": { "成交产品": "陪跑90天", "成交金额": "39800" },
  "tags": ["冷淡期", "判断对方态度"]
}
字段说明
externalId必填。你那边的客户 id。同一个值永远对应 IdeaHub 里的同一条客户
alias化名。不要传真名，IdeaHub 里全部是脱敏的
tierS / A / B / C
stagelead 新客资 · wechat 已加微 · profiled 已建档 · consulted 已咨询 · coaching 已陪跑 · renewed 已续费 · lost 已流失
aiSituationAI 情况分析。在客户详情页第 ⑤ 区单独显示
aiUserAI 用户分析。第 ⑥ 区单独显示。两者必须分开传，不要合成一段
female male
relation deal		自由键值对，会和已有内容合并，不会互相覆盖
tags标签名字数组。名字必须在 IdeaHub 的标签字典里，不在的会被忽略 —— 这是「全站统一标签」的前提，不接受随手造的新标签。要加标签请让管理员在界面上加

没传的字段不会被清空。业务人员在界面上手改过的等级、阶段、化名，也不会被你的推送冲掉。

返回 {"ok":true,"id":74,"created":false} —— created 为 false 表示这次是更新已有客户。

POST /api/ingest/client/delivery 显示在客户详情页第 ⑧ 区

追加一条交付记录。客户必须已经建过档，否则返回 404。

{
  "externalId": "t2-8891",
  "happenedAt": "2026-08-24",
  "kind": "陪跑",
  "summary": "第三周复盘"
}

二、市场分析结果 技术1

业务人员在技术1 的结果页点「保存到 IdeaHub」时调这个口。 存到哪里，由他点了哪个按钮决定，后端不猜。

POST /api/ingest/save 三个去处，由 type 决定
type存到哪什么时候用
demand用户需求从评论 / 私信里提炼出的一条用户需求
idea灵感池（不是正式库）一个选题想法、一个可以做的方向
reference对标作品台账分析过的别人家的视频，指标一起带过来

不会自动进正式库。正式库仍然只能由业务人员在 IdeaHub 里确认转入 —— 这是任务表写死的规则。

{
  "type": "demand",
  "sourceRef": "t1-vid-5521",
  "sourceUrl": "https://v.douyin.com/xxxx",
  "title": "想让对方主动联系自己",
  "quote": "评论区高频：为什么我不主动他就不找我",
  "scene": "暧昧期停滞",
  "realGoal": "确认对方是否有意愿",
  "tags": ["暧昧期", "推进不动"]
}

type: "idea" 时用 title + content； type: "reference" 时用 title + channel （persona / matrix / live，默认 matrix） + metrics（如 {"曝光":220000,"收藏":8100}）+ publishedAt。

字段说明
sourceRef必填。你那边这条分析结果的 id。同一个值重复保存不会产生第二条记录，只会更新原来那条
sourceUrl原视频 / 原评论的地址。IdeaHub 里每条资料都会显示「来源」，点得开原始出处
tags同上，只认字典里已有的标签名

返回 {"ok":true,"type":"demand","id":2,"created":true,"board":"demands"}

POST /api/ingest/analysis?channel=persona 整份采集分析 JSON 原样推进来

把技术1 导出的那份 JSON 原样 POST 进来就行 —— 不用拆字段、不用转 CSV、不用改导出格式。 它会落进「真人作品 / 矩阵作品」的对标账号里，业务人员点开卡片就能看到封面、 账号粉丝数、公开互动数、AI 的视频七问和评论五问（带原话证据）、高赞评论、 带时间码的完整逐字稿。 

curl -X POST "https://xm.xingxingqule.com:9443/api/ingest/analysis?channel=persona" \
     -H "Authorization: Bearer $KEY" \
     -H "Content-Type: application/json; charset=utf-8" \
     --data-binary @女孩子无聊的本质是生命力的匮乏.json

用推送脚本更省事，一次推一个文件夹：

export IDEAHUB_KEY=ih_tech1_你的密钥
python3 推送到ideahub.py analysis persona 今天跑出来的结果/

channel 决定进哪个板块，写在 URL 上，JSON 里一个字都不用动：

channel落到哪
persona真人作品 → 对标账号
matrix矩阵作品 → 对标账号（不带 channel 时的默认值）
live真人直播 → 对标直播
persona,matrix同时进两个板块 —— 同一个视频既是真人对标也是矩阵对标时用

JSON 里这些字段会被读出来。其余字段一个不丢，原样存着，将来界面上要显示随时能取：

JSON 字段用途
task_id幂等依据。同一个 task_id 推一万次也只有一条记录，放心重试。没有它就退回用 source_url 算指纹
title / post_title / display_title / cover_title作品标题，按这个顺序取第一个非空的。cover_title 是封面 OCR、带识别误差，所以放最后
source_url原作品链接，界面上「打开原作品」用
platformxiaohongshu / douyin / kuaishou / weibo / bilibili / wechat，认不出来算「其他」
account.*对标账号台账会自动建档：账号名、主页、粉丝数、简介。粉丝数每次推送都刷新
engagement.*「4万」「3.2万」这种缩写会被读成数字（40000 / 32000），能排序能筛选
topics当标签名来认，只认 IdeaHub 标签字典里已有的，其余忽略
ai_analysis.video.items视频七问。键的顺序就是显示顺序，别打乱
ai_analysis.comments.items评论洞察，连 evidence_comments 里的原话一起显示
media_assets.video.cover_image_b64封面原图，强烈建议给这个 —— 见下面「关于封面清晰度」
media_assets.video.*封面地址（收到时就下到 IdeaHub 本地，平台链接过期也不受影响）、时长、尺寸、清晰度
images[]图文笔记的正文图片；image_b64 优先，source_url 只作临时备用
video_text + video_text_meta逐字稿。有段没识别成功（chunks_succeeded < chunks_total）界面上会标出来
comments / comment_summary高赞评论原文 +「扫了多少条」这些说明
schema_version记下来，以后格式换代了两边对得上

关于封面清晰度（请务必看一眼）

平台给的 thumbnail_url 是 CDN 的预览变体（小红书那份是 !nd_prv_wlteh_jpg_3）： 尺寸写着 1080×1441，实际只有 27KB，每像素 0.017 字节 —— 人脸糊成一片。 而且那个签名只对这一个变体有效，换成原图或别的清晰度后缀一律 403， 所以 IdeaHub 这边无论怎么处理都救不回来。

解决办法：把整张封面直接放进 JSON。你那边为了做封面 OCR 本来就截过原始帧，给出来是顺手的事：

{
  "media_assets": {
    "video": {
      "cover_image_b64": "data:image/jpeg;base64,/9j/4AAQSkZJRg...",
      "thumbnail_url": "http://sns-webpic-qc.xhscdn.com/...",
      "duration_seconds": 296.077
    }
  }
}
写法data:image/jpeg;base64,xxx 和光秃秃的 base64 都收，不用纠结
格式JPEG / PNG / WebP / GIF / AVIF。按真实字节认，不看声明的 mime
大小单张上限 3MB。一张 1080×1920 的清晰竖图约 200~500KB，正常
请求体上限这个接口放宽到 32MB（其他接口仍是 1MB），给图文笔记整组图片留空间
没给怎么办自动退回去下 thumbnail_url，行为和以前完全一样，不给也不会报错
存哪收到就落成本地文件，之后一律走 GET /api/works/:id/cover，不受签名过期影响
会不会撑爆库不会。图落地之后会从存档的 JSON 里摘掉，只留一句说明，其余字段一个不动

图文图片不能只传临时地址

小红书图文地址路径中的 202608241555 是失效时间。技术1采集后隔天才推， IdeaHub 收到时地址已经 403；即使 JSON 里有完整 OCR，也无法凭文字还原原图。

完整归档时应把技术1本地保留的图片本体一起带来。最新版推送脚本会按 filename 在 JSON 同目录、images/、同名目录或 task_id 目录中自动找图并附入请求：

"images": [{
  "index": 1,
  "filename": "image_01.webp",
  "source_url": "http://sns-webpic-qc.xhscdn.com/临时地址",
  "image_b64": "data:image/webp;base64,UklGR...",
  "text": "这张图的 OCR 文字"
}]
推荐字段images[].image_b64；也兼容 image_base64、content_b64、data_url
优先级图片本体优先；没有本体才尝试 source_url
格式与大小JPEG / PNG / WebP / GIF / AVIF；单张不超过 3MB，最多保存 20 张
失败提示返回 imagesExpected、imagesStored 和 warnings[]，不再静默丢图
重推保护imagesStoredNow 是本轮新保存数；本轮失败的序号会保留以前已落地的图片

旧记录显示“图片已过期”时，用同一个 task_id重推即可补图，不会多建一条作品。

{
  "ok": true,
  "taskId": "f90d29b0a27b",
  "title": "女孩子无聊的本质是生命力的匮乏",
  "id": 174, "created": true,
  "imagesExpected": 8, "imagesStored": 8, "warnings": [],
  "results": [{ "channel": "persona", "id": 174,
                "created": true, "accountId": 9, "tagsApplied": 2,
                "imagesExpected": 8, "imagesStored": 8, "imagesStoredNow": 8 }]
}

不覆盖人写的东西。台账里的「备注 / 复盘」业务人员写过就不会被推送冲掉（空着才填 AI 的一句话主题）， 账号的「定位」同理。标题、链接、互动数这些客观事实每次推送都会刷新。

请求体上限 32MB（其他接口是 1MB）。普通视频分析仍只有几十 KB；图文笔记可以把整组图片一起带来。

这个口子只写对标那半边，永远不会动「自己账号」的数据。

三、错误码

状态含义
401没带 Authorization 头，或 key 无效 / 已停用
403key 的权限不对（技术1 的钥匙去调技术2 的口）
400必填字段缺失或取值不合法，error 字段里写了具体是哪个

四、给对接方的三条提醒

1
externalId / sourceRef 一旦定下来就别改

它们是「同一条东西」的唯一依据。改了就会在 IdeaHub 里多出一条重复记录，而且没人能一眼看出这两条其实是一个。

2
标签只能用字典里已有的

需要新标签就找 IdeaHub 管理员在「标签与对接」页加一个，全站立刻可用。这是为了让「分手」在灵感、需求、案例、客户档案里是同一个词。

3
失败要重试

接口是幂等的，同一条重复推送不会产生副本，放心重试。
