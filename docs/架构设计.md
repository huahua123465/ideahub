# 内部灵感库 IdeaHub — 技术架构设计

> 面向公司内部的两级灵感管理系统：**灵感池**（人人可提、人人可见）→ **正式库**（评审采纳后立项）。
> 部署目标：单台 VPS（4 vCPU / 3.9G 内存 / 77G 磁盘，已有 Docker）。

---

## 一、核心设计决策

### 1. 一张表，两个视图 —— 不是两个库

这是整个系统最关键的一条。灵感的两级不是两份存储，而是同一条记录的 `status` 字段取值不同：

```
灵感池视图  = SELECT * FROM ideas WHERE status IN ('pending','reviewing')
正式库视图  = SELECT * FROM ideas WHERE status = 'adopted'
```

**为什么不能做成两个库：**

| 问题 | 两个独立库 | 一张表 + 状态 |
|---|---|---|
| 灵感被否决半年后重新捡起 | 记录要搬回去，评论/投票历史断裂 | 改一次状态，全部历史跟着走 |
| 统计"采纳率" | 要跨库 join，还对不上 | 一条 `GROUP BY status` |
| 谁在什么时候采纳的 | 无处记录 | activities 表全程留痕 |
| 搜索"我提过的所有灵感" | 查两遍再合并 | 一次查询 |

对使用者来说，界面上看到的仍然是"两个库"（两个 Tab）——**分离发生在视图层，不在存储层**。

### 2. 存数据库，不存文件

灵感条目的特征是：短、字段固定、要按状态/标签/时间/热度排序筛选、要聚合统计。这是关系数据库的主场。PostgreSQL 存几十万条灵感毫无压力。

（正文用 Markdown 格式存在 `content` 字段里 —— 内容是 Markdown 文本，但**载体是数据库行**，这样既保留了纯文本的可读性，又能被 SQL 检索。）

## 二、技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite | 你现有项目就是这套，复用组件和构建流程 |
| UI 组件 | shadcn/ui + Tailwind CSS | 无运行时依赖，产物小 |
| 后端 | NestJS（Node 22）或 FastAPI（Python） | 按你团队熟悉度选，接口设计完全一样 |
| 数据库 | PostgreSQL 16 | 事务、全文检索、JSONB 一站解决 |
| 中文搜索 | 关键词 ILIKE + 自研 `cn_similarity()` | 见下方「关于中文搜索」——**不用 pg_trgm，也不用 zhparser** |
| 认证 | 企业微信 / 飞书扫码登录 | 免去自建账号体系，天然对应公司组织架构 |
| 反向代理 | Caddy 2 | 自动申请续期 HTTPS 证书，配置只要 3 行 |
| 部署 | Docker Compose | 你机器上 Docker 已就绪 |

### 内存预算（关键约束）

你这台机器现在已用 1.8G / 3.9G，还跑着 xray、x-ui 等服务。IdeaHub 的占用规划：

| 容器 | 限额 | 说明 |
|---|---|---|
| postgres | 512 MB | `shared_buffers=128MB`，小库足够 |
| api（后端） | 320 MB | Node 加 `--max-old-space-size=256` |
| caddy | 32 MB | 同时托管前端静态产物，不单独起 nginx |
| **合计** | **≈ 864 MB** | 留足余量给你现有服务 |

> 实现里没有 Redis，也没有对象存储。通知是同步 fetch 到群机器人（失败不影响主流程），
> 定时任务跑在后端进程内。附件上传还没做。少一个组件就少一份运维负担，等真需要再加。

> 这也是我不推荐 Baserow（官方建议 4G 起）和 Discourse（≥2G）的原因 —— 你这台机器上它们会和现有服务抢内存。

## 三、数据模型

```sql
-- 状态枚举：两级库的分界就在这里
CREATE TYPE idea_status AS ENUM (
  'draft',      -- 草稿，仅自己可见
  'pending',    -- 待评审  ┐
  'reviewing',  -- 评审中  ┘ 灵感池（预备库）
  'adopted',    -- 已采纳    正式库
  'rejected',   -- 已否决
  'archived'    -- 已归档
);

CREATE TABLE ideas (
  id             BIGSERIAL PRIMARY KEY,
  code           TEXT UNIQUE,              -- 采纳时生成：IDEA-2026-0043
  title          TEXT NOT NULL,
  content        TEXT NOT NULL,            -- Markdown 正文
  category       TEXT NOT NULL,            -- 产品 / 技术 / 运营 / 流程 / 其他
  tags           TEXT[] DEFAULT '{}',
  status         idea_status NOT NULL DEFAULT 'pending',
  author_id      BIGINT REFERENCES users(id),
  is_anonymous   BOOLEAN DEFAULT false,    -- 匿名提交，降低发言门槛
  vote_count     INT DEFAULT 0,            -- 物化计数，避免每次 COUNT
  comment_count  INT DEFAULT 0,
  hot_score      REAL DEFAULT 0,           -- 热度，定时任务重算
  -- 采纳后才填充的字段
  owner_id       BIGINT REFERENCES users(id),   -- 立项负责人
  adopted_at     TIMESTAMPTZ,
  adopted_by     BIGINT REFERENCES users(id),
  doc_url        TEXT,                          -- 关联的方案文档
  view_count     INT DEFAULT 0,
  created_at     TIMESTAMPTZ DEFAULT now(),
  updated_at     TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_ideas_status_hot ON ideas(status, hot_score DESC);
CREATE INDEX idx_ideas_tags       ON ideas USING GIN(tags);

-- 投票：唯一索引天然防重复投票
CREATE TABLE idea_votes (
  idea_id  BIGINT REFERENCES ideas(id) ON DELETE CASCADE,
  user_id  BIGINT REFERENCES users(id),
  created_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (idea_id, user_id)
);

-- 讨论
CREATE TABLE idea_comments (
  id         BIGSERIAL PRIMARY KEY,
  idea_id    BIGINT REFERENCES ideas(id) ON DELETE CASCADE,
  user_id    BIGINT REFERENCES users(id),
  parent_id  BIGINT REFERENCES idea_comments(id),  -- 支持一级回复
  body       TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 审计流水：谁在什么时候把状态改成了什么，附理由
CREATE TABLE idea_activities (
  id          BIGSERIAL PRIMARY KEY,
  idea_id     BIGINT REFERENCES ideas(id) ON DELETE CASCADE,
  actor_id    BIGINT REFERENCES users(id),
  action      TEXT NOT NULL,        -- created / voted / commented / status_changed
  from_status idea_status,
  to_status   idea_status,
  reason      TEXT,                 -- 否决时必填，这条很重要
  created_at  TIMESTAMPTZ DEFAULT now()
);
```

**`idea_activities` 值得单独说一句**：它让"为什么这条灵感被否决了"变成可查的事实。没有这张表，半年后没人记得当初的判断依据，同一个想法会被重复提出、重复否决。

## 四、状态机

```
                  ┌──────────────────────────────────────┐
                  │                                      ↓
draft ──提交──> pending ──评审委员认领──> reviewing ──采纳──> adopted ──> (立项)
                  │                          │
                  │                          └──否决(必填理由)──> rejected
                  │                                                  │
                  └────────────── 90天无人处理，自动归档 ──> archived <┘
                                                                 (可重新激活)
```

**流转规则：**

- `pending → reviewing`：任意评审委员点"认领"，防止多人重复评估
- `reviewing → adopted`：需满足条件之一 —— 评审委员拍板，或投票数 ≥ 阈值（比如 10 票）触发强制评审
- `任意 → rejected`：**必须填理由**，理由写进 activities 并通知提交人
- `rejected/archived → pending`：任何人可以"重新提出"，历史评论保留，新增一条 activity

## 五、后端处理逻辑

### 提交灵感 `POST /api/ideas`

```
1. 校验：标题 4-80 字，正文 ≥ 20 字，分类在枚举内
2. 查重：用 title_similarity() 检索，相似度 > 0.2 的前 3 条返回给前端
   → 前端提示"是不是和这几条重复？"，但不阻断提交（阻断会劝退提交欲望）
3. 事务：
   INSERT INTO ideas (status='pending')
   INSERT INTO idea_activities (action='created')
4. 异步：推送到企业微信/飞书群机器人 —— "张三提了个新灵感：xxx"
5. 返回 201 + 完整对象，前端乐观插入到列表顶部
```

### 投票 `POST /api/ideas/:id/vote`

```
INSERT INTO idea_votes (idea_id, user_id)
ON CONFLICT DO NOTHING          -- 主键冲突即重复投票，静默忽略
RETURNING *;
-- 若真的插入了，触发器同步 ideas.vote_count += 1
```

用**唯一主键**而不是应用层判重，是因为并发双击时应用层的"先查后写"会漏。数据库约束是唯一可靠的那道闸。

### 采纳 `PATCH /api/ideas/:id/status`

```sql
BEGIN;
  -- 1. 行级锁，防止两个评审同时采纳
  SELECT * FROM ideas WHERE id = $1 FOR UPDATE;
  -- 2. 权限校验：actor 必须是 reviewer 角色
  -- 3. 状态合法性校验：reviewing → adopted 合法，rejected → adopted 需先回 pending
  -- 4. 生成正式库编号（年度序列）
  UPDATE ideas SET
    status     = 'adopted',
    code       = 'IDEA-' || to_char(now(),'YYYY') || '-' || lpad(nextval('idea_code_seq')::text, 4, '0'),
    adopted_at = now(),
    adopted_by = $actor,
    owner_id   = $owner
  WHERE id = $1;
  -- 5. 留痕
  INSERT INTO idea_activities (idea_id, actor_id, action, from_status, to_status)
       VALUES ($1, $actor, 'status_changed', 'reviewing', 'adopted');
COMMIT;
-- 6. 事务外异步：通知提交人 + 群机器人播报
```

### 热度排序

避免"最早提的永远排第一"，用带时间衰减的公式（Hacker News 式）：

```
hot_score = (vote_count + comment_count * 2 + 1) / POWER(hours_since_created + 2, 1.5)
```

**分子里的 `+1` 是必须的**：没有它，刚提交、还没人投票的灵感 hot_score 恒等于 0，
会直接沉到列表最底下 —— 提了就看不见，等于没提。（Hacker News 是靠"作者自动投自己一票"
拿到这个基础分的。）

写入时机分两处：`vote_count` / `comment_count` 变化时由触发器立刻重算；
**时间衰减没有任何写操作会触发**，所以后端进程内还跑了一个每 15 分钟的定时重算。

### 关于中文搜索

踩过一个坑值得记下来：**`pg_trgm` 在 C locale 下对中文一个 trigram 都切不出来**，
`similarity()` 恒等于 0，而且不报错 —— 是静默失效。数据库的 locale 不该由应用来假设。

所以实现里自己写了 `cn_similarity()`：按字切二元组算 Jaccard 相似度，与 locale 无关。
英文仍走 `pg_trgm`，`title_similarity()` 取两者的大值。提交查重用它。

列表搜索则是直接 `ILIKE`，没有建全文索引 —— 几万条以内够用。真到了需要的时候
再上 `zhparser` 或外置搜索引擎，那是后话。

## 六、API 一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ideas?status=pending&sort=hot&page=1` | 灵感池列表 |

## 七、权限模型（保持极简）

| 角色 | 权限 |
|---|---|
| 全员 | 看全部（除他人 draft）、提交、评论、投票 |
| 评审委员 | 全员权限 + 状态流转 + 指派负责人 |
| 管理员 | 全部 + 删除、管理标签、管理角色 |

**不做部门级隔离**。内部灵感库的价值恰恰在于跨部门看见彼此的想法 —— 加了隔离墙，它就退化成了几个各自冷清的小池子。

## 八、部署

```yaml
# docker-compose.yml（骨架）
services:
  db:
    image: postgres:16-alpine
    environment: [POSTGRES_DB=ideahub, POSTGRES_PASSWORD=***]
    volumes: ["./data/pg:/var/lib/postgresql/data"]
    deploy: { resources: { limits: { memory: 512M } } }

  api:
    build: ./server
    environment: [DATABASE_URL=postgres://..., NODE_OPTIONS=--max-old-space-size=256]
    depends_on: [db]
    deploy: { resources: { limits: { memory: 320M } } }

  caddy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes: ["./Caddyfile:/etc/caddy/Caddyfile", "./web/dist:/srv"]
    deploy: { resources: { limits: { memory: 32M } } }
```

```
# Caddyfile —— 自动 HTTPS
idea.yourcompany.com {
    root * /srv
    handle /api/* { reverse_proxy api:3000 }
    handle { try_files {path} /index.html; file_server }
}
```

**每日备份**（灵感库最怕的是丢数据，不是宕机）：

```bash
0 3 * * * docker exec ideahub-db pg_dump -U postgres ideahub | gzip > /backup/ideahub-$(date +\%F).sql.gz
```

## 十、上线后最容易踩的坑

1. **冷启动**：空池子没人愿意第一个提。上线前先自己灌 20-30 条真实灵感，让新人打开就看到内容。
2. **提了没回应**：最伤人的不是被否决，是石沉大海。所以设了 90 天自动归档 + 否决必填理由 —— **给每条灵感一个明确的结局**。
3. **提交门槛**：表单字段越多，提交量越低。必填只留标题 + 正文 + 分类，其余全是可选。匿名选项也是为这个。
4. **评审积压**：如果评审委员两周不看，池子就死了。建议群机器人每周一播报"当前待评审 N 条，最久的已等待 M 天"。
