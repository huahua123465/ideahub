# IdeaHub 内容采集部署

内容采集由独立的 `collector` 容器执行，IdeaHub Node 后端负责登录鉴权、权限判断和固定路径代理。浏览器不能直接访问 Collector，也不能获得内部令牌、平台 Cookie 或 AI 密钥。

## 部署结构

```text
浏览器
  └─ HTTPS → IdeaHub/Caddy
                └─ /api/collector/* → IdeaHub api（登录与权限）
                                           └─ Docker 内网 → collector:5000
```

- `collector` 只有 Compose 的 `expose: 5000`，没有宿主机 `ports`。
- IdeaHub 不依赖 Collector 才能启动。Collector 构建或运行失败时，现有网站仍可正常使用，采集页会显示服务不可用。
- SQLite、登录态和媒体位于 `/opt/ideahub-collector/`，不进入 Git 仓库，也不会混入 VPS 自动备份提交。
- 本功能不修改 PostgreSQL 结构，不需要执行迁移 SQL。

## 首次部署前准备

以下操作只在 VPS 执行一次。先进入 IdeaHub 仓库，并确认 VPS 工作区的备份变化已经提交和推送，再拉取新代码。

### 1. 创建仓库外持久目录

Collector 镜像以固定用户 `10001:10001` 运行：

```bash
sudo install -d -m 0700 -o 10001 -g 10001 /opt/ideahub-collector/state
sudo install -d -m 0750 -o 10001 -g 10001 /opt/ideahub-collector/output
```

不要把目录改到 IdeaHub 仓库内。`state` 中有 SQLite 和小红书登录态，`output` 中有图片、视频和分析结果。

### 2. 备份并补充 VPS `.env`

不要用 `.env.example` 覆盖 VPS 已有 `.env`。先在仓库外做一份只供管理员读取的备份，再把缺少的变量逐项合入现有文件。

生成内部令牌：

```bash
openssl rand -hex 32
```

把生成结果只写入 VPS `.env`：

```dotenv
COLLECTOR_INTERNAL_TOKEN=这里填写刚生成的64位十六进制值
COLLECTOR_STATE_PATH=/opt/ideahub-collector/state
COLLECTOR_OUTPUT_PATH=/opt/ideahub-collector/output
```

同一个 `COLLECTOR_INTERNAL_TOKEN` 会由 Compose 同时传给 `api` 和 `collector`，无需在两个地方重复配置。不要把值发送到聊天、日志或浏览器。

### 3. 配置分析供应商

只填写实际使用的一组供应商密钥：

```dotenv
VIDEO_MODEL_PROVIDER=moxus
MOXUS_API_KEY=...
DEEPSEEK_API_KEY=...
```

若使用 OpenRouter 或 Whisper，按 `.env.example` 补充对应变量。留空的供应商不会获得密钥。

### 4. 配置推送 IdeaHub 的机器密钥

Collector 推送到真人作品/矩阵作品时需要 `tech1` 机器密钥：

```dotenv
IDEAHUB_API_KEY=现有技术1密钥
```

可以复用当前技术1传入 IdeaHub 的有效密钥。如果必须新建，管理员在 IdeaHub 的“标签与对接”中创建技术1密钥；明文只显示一次，应立即写入 VPS `.env`，不要提交到仓库。

## 分阶段上线

### 1. 拉取并检查配置

```bash
git status --short --branch
git pull --ff-only origin main
docker compose config >/dev/null
```

如果 `docker compose config` 提示变量或挂载目录有误，先停止，不要重启现有 IdeaHub。

### 2. 只构建 Collector

```bash
docker compose build collector
docker compose up -d collector
docker compose ps collector
docker compose logs --tail=100 collector
```

首次构建会下载 Chromium、FFmpeg、OCR 和 Python 依赖，耗时和镜像体积会明显高于普通前端更新。构建期间旧 IdeaHub 容器继续运行。

健康检查：

```bash
docker compose exec -T collector curl -fsS http://127.0.0.1:5000/health
```

正常响应应包含 `"ok":true`。若 Collector 未健康，不要切换主站；先检查日志、目录权限和内部令牌。

### 3. 更新 IdeaHub API

Collector 健康后再更新整套服务：

```bash
docker compose up -d --build
docker compose ps
curl -fsS http://127.0.0.1:18080/api/health
```

这一步会重新构建并切换 IdeaHub 容器，中间可能有几秒不可访问，不属于热更新。

### 4. 页面验收

管理员在 IdeaHub 中依次验证：

1. 打开“内容采集”，服务状态正常；
2. 点击小红书登录，页面显示服务器生成的二维码；
3. 手机扫码后账号状态变为已登录；
4. 提交一条允许平台的 HTTPS 分享链接；
5. 查看排队、进度、结果、图片或视频；
6. 推送到真人作品或矩阵作品；
7. 用普通成员账号确认只能看到自己创建的任务，且没有删除和平台登录权限。

## 账号隔离与公开无登录模式

- 日常浏览使用的个人小红书账号不建议长期登录 VPS。数据中心 IP 与服务器浏览器可能触发平台的设备或会话限制，优先使用独立的采集专用账号。
- “退出采集账号”只删除 `/var/lib/collector/state` 中的小红书 Cookie、storage state、二维码、账号资料与内部备注；不会删除任务、图片、分析结果或 IdeaHub 数据。
- 平台未返回昵称、小红书号或用户 ID 时，页面必须显示“账号身份未确认”。管理员可以添加内部备注，但备注不代表平台验证。
- “公开无登录模式”不会读取或刷新服务器保存的 Cookie/storage state。它仍会尝试采集公开正文、图片和公开账号页，但评论、互动量或受登录限制的内容可能不完整。
- 已创建任务会把 `session_mode` 写入结果；“更新数据”沿用原任务的模式，避免公开任务在刷新时意外启用登录态。

## 资源限制

Compose 已固定以下保守值：

- 采集并发 `1`；
- OCR、OMP、OpenBLAS、MKL、NumExpr、ONNX、Web线程均为 `1`；
- CPU 上限 `1.5` 核；
- 内存上限 `1536MB`；
- PID 上限 `256`；
- Chromium `/dev/shm` 为 `256MB`；
- 队列默认最多 `10` 条；
- 单视频默认最多 `600` 秒、下载最多 `500MB`；
- 二维码最长保留 `180` 秒。

容器同时启用 `cap_drop: ALL`、`no-new-privileges` 和非 root 用户。不要为解决 Chromium 问题添加 `privileged: true` 或开放 5000 端口。

## 磁盘维护

建议每周检查一次：

```bash
du -sh /opt/ideahub-collector/state /opt/ideahub-collector/output
df -h /opt/ideahub-collector/output
```

建议在 20GB 前预警。删除历史任务应通过 IdeaHub 管理员界面执行，让 SQLite 记录和文件一起删除；不要直接对 `output` 执行批量 `rm`。需要保留分析 JSON、删除大媒体时，应先由开发人员增加明确的归档功能。

## 故障与回滚

- Collector 构建失败：不执行主站切换，旧 IdeaHub 继续运行。
- Collector 启动失败：`docker compose stop collector`，IdeaHub 其他功能不受影响。
- 新版 API 有问题：先停止 Collector；由本地开发端对集成提交执行 `git revert` 并推送，VPS 再 `git pull --ff-only` 和重建。不要在 VPS 使用强制推送或删除数据库/卷。
- 重新构建不会删除 `/opt/ideahub-collector/` 中的数据。
- 回滚不需要 PostgreSQL SQL，因为本次没有数据库结构变更。

## 后续日常更新

同事和 VPS 继续共用同一个 IdeaHub 仓库：

```text
本地修改前先 pull
→ 修改并验证
→ push
→ VPS 确认备份改动已提交推送
→ VPS pull
→ docker compose up -d --build
```

如果仅前端或普通后端变化，仍按原流程发布；如果修改 Collector、Compose 或 `.env` 变量，必须按本文先审核资源和配置。
