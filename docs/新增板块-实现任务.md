# 新增五个业务板块 —— 实现任务

来源：《情感赛道全链路业务 1.0》（ZWWD 女性情感业务系统 V1.0，2026.08）。
本文把 PDF 里的业务结构落成可执行的开发任务。

---

## 一、板块与 PDF 的对应关系

导航从「灵感池 / 正式库 / 统计」扩成八个，新增的五个各自对应 PDF 的哪一章：

| 新板块 | PDF 出处 | 承载的业务 |
|---|---|---|
| **真人作品** | 02 前端获客系统（真人 IP） | 真人 IP 四大内容支柱的作品沉淀 + 对标账号研究 |
| **矩阵作品** | 02 前端获客系统（非真人矩阵） | 批量生产、多账号分发、关键词引流的素材与账号台账 |
| **真人直播** | 03 直播系统 | 直播场次记录（主题干货 / 案例拆解 / 连麦诊断）+ 对标直播观察 |
| **销售转化** | 04 私信筛选 + 05 建档 + 06 单次咨询 | 客资分级标准、四维筛选、建档必收字段、各场景话术 |
| **后端交付** | 07 陪跑 + 08 课程 + 09 案例资产化 | 产品阶梯、课程分层、陪跑交付循环 |

**PDF 第 12 页的判断是这次设计的主线**：「下一步最重要的不是继续无限扩选题，
而是把前端—中端—后端之间的交接标准做清楚」。所以五个板块不是五个孤立的表格，
而是按 `前端(作品/矩阵/直播) → 中端(销售转化) → 后端(交付)` 排成一条链路，
导航顺序也按这条链路排。

### 每个板块的两个小板块

用户明确要求真人作品分「自己账号」和「对标账号」两块，矩阵作品和真人直播同构。
所以三个前端板块统一用同一组 tab：

```
[ 自己账号 ]  [ 对标账号 ]
```

销售转化和后端交付不分自己/对标，改为按内容类型分小板块（见下表）。

## 二、数据模型

不给五个板块各建一张表 —— 前端三个板块的字段几乎完全一样，
拆开会变成三份互相抄的代码。最终只加 **三张表**。

### 表 1 `channel_accounts` —— 账号台账（自己的 + 对标的）

```sql
channel   persona | matrix | live     -- 属于哪个板块
side      own | benchmark             -- 自己账号 / 对标账号
platform  小红书 / 抖音 / 视频号 / 快手 / 其他
handle    账号名
url       主页链接
followers 粉丝数
positioning  定位 / 人设（PDF 02：真人IP=建立深度信任，矩阵=扩大流量覆盖）
note      备注；对标账号写"为什么值得对标"
```

### 表 2 `works` —— 作品与直播场次

```sql
channel   persona | matrix | live
side      own | benchmark
account_id -> channel_accounts        -- 哪个号发的
title     标题 / 直播主题
url       作品链接 / 回放链接
pillar    内容支柱（PDF 02 真人IP四大支柱）
published_at  发布日期 / 开播日期
metrics   JSONB                       -- 见下
note      备注 / 复盘
```

**`metrics` 用 JSONB 而不是固定列**：三个板块看的指标不一样
（PDF 10/11 页分别给了内容层和直播层的指标），写死成列会让表里一半字段永远是空的。
指标键在代码里集中定义一处，加指标不用改表结构。

- 真人作品 / 矩阵作品（PDF 11 内容层）：`曝光 完播 收藏 私信 主页访问`
- 真人直播（PDF 11 直播层）：`在线峰值 停留分钟 连麦数 私信 预约`

### 表 3 `playbook_items` —— 销售转化 + 后端交付

这两块都是「分类 + 标题 + 正文 + 排序」的结构化文档，共用一张表：

```sql
board     sales | delivery
section   -- 即小板块
          sales:    tier(客资分级) / filter(四维筛选) / intake(建档字段) / script(话术)
          delivery: product(交付产品) / flow(交付流程)
label     小分类：话术场景 / 客资等级 / 产品类型 / 流程节点
title     标题
body      正文
meta      JSONB —— 不定字段（负责人角色、核心指标、层级、适用等级…）
sort      排序
```

三张表都跟着现有习惯走：`schema.sql` 里 `CREATE TABLE IF NOT EXISTS` + 幂等，
`db:init` 跑一次就能升级已有库。

## 三、后端

`server/src/routes/boards.mjs`（新增，一个文件搞定三张表）：

| 端点 | 说明 |
|---|---|
| `GET/POST /api/accounts`，`PATCH/DELETE /api/accounts/:id` | 账号台账，按 `channel`/`side` 过滤 |
| `GET/POST /api/works`，`PATCH/DELETE /api/works/:id` | 作品与直播，按 `channel`/`side` 过滤 |
| `GET/POST /api/playbook`，`PATCH/DELETE /api/playbook/:id` | 销售转化 / 后端交付，按 `board`/`section` 过滤 |

- 复用 `lib/http.mjs` 的 `sendJson / readJson / q / need / badRequest`，
  路由挂载沿用 `mount(router)` 惯例。
- 权限跟现有的「人人可评审」保持一致：**登录即可读写，删除限管理员**。
  这三张表是团队共同维护的台账，卡权限只会让人懒得录。
- 写操作后 `publish('board:updated', { board })`，复用已有的 SSE 通道 ——
  几个人同时录数据时不用互相喊"你刷新一下"。

## 四、前端

八个 tab 会把顶栏挤爆，所以 `.nav` 要能横向滚动（`overflow-x:auto` + 隐藏滚动条），
按钮内边距收窄。

### 通用板块渲染器（关键决策）

不为五个板块写五套表格代码。新增两个文件：

- **`web/src/boards.js`** —— 纯数据：每个板块的字段定义（列名、类型、下拉选项、
  哪些进表格、哪些进编辑弹窗）。
- **`web/src/views/board.js`** —— 一个渲染器：读字段定义 → 画小板块 tab、
  画表格、画「＋ 新增」弹窗、增删改调接口。

这样五个板块 = 一份渲染器 + 五段配置。以后加第六个板块只需要写配置。

### 每个板块的小板块与列

| 板块 | 小板块 | 表格列 |
|---|---|---|
| 真人作品 | 自己账号 / 对标账号 | 标题、账号、支柱、发布日期、曝光、完播、收藏、私信、链接 |
| 矩阵作品 | 自己账号 / 对标账号 | 同上（支柱换成"选题方向"） |
| 真人直播 | 自己直播 / 对标直播 | 主题、账号、日期、时长、在线峰值、停留、连麦、私信、预约、回放 |
| 销售转化 | 客资分级 / 四维筛选 / 建档字段 / 话术库 | 等级/场景、标题、正文、适用对象 |
| 后端交付 | 交付产品 / 交付流程 | 类型、名称、层级、解决什么、负责人、核心指标 |

账号台账做成每个前端板块顶部的一块折叠区（「账号」按钮展开），
不单独占 tab —— 账号数量少，不值得再多三个入口。

## 五、默认数据（全部来自 PDF，不是占位文本）

`server/src/seed-boards.mjs`（新增，可重复执行，已存在则跳过）：

- **后端交付**：
  - 产品阶梯 7 级（免费内容 → 直播/私信 → 低价课/资料 → 单次咨询 →

  - 陪跑两条线（关系项目型 / 长期成长型，PDF 07）
  - 陪跑交付循环 7 节点（目标确认 → 阶段判断 → 制定策略 → 客户执行 →
    收集反馈 → 复盘校准 → 进入下一节点，PDF 07）
  - 每条带上 PDF 10 页的负责人角色和 11 页的核心指标

## 六、执行顺序

1. `schema.sql` 加三张表 + 枚举 + 索引
2. `routes/boards.mjs` + 挂载到 `index.mjs`
3. `seed-boards.mjs` 灌默认数据
4. `boards.js` 字段定义 + `views/board.js` 渲染器
5. `index.html` 五个 tab + 五个 section、`main.js` 接进 `go()`、`styles.css` 样式
6. `docker compose up -d --build api` + `db:init` + seed，逐个板块验收

## 七、明确不做

- 不动灵感池 / 正式库 / 统计的任何现有逻辑和数据
- 不做客户档案和案例库（PDF 05/09 的客户级数据涉及聊天记录、照片等敏感材料，
  值得单独设计权限和脱敏，不该混在这批台账里顺手做）
- 不做数据漏斗看板（PDF 11）—— 指标要先有人录进来才有意义，等这批台账跑起来再说
