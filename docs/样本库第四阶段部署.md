# 样本库第四阶段部署

本阶段属于 C 类发布。它新增 21 张表、复合约束、LSH 索引和脏状态触发器。仅拉取代码并重建容器不会改变已有数据库，必须先备份，再由 VPS 维护者手工执行迁移。迁移是加法式的；Stage 3 应用可忽略新增表。

## 发布前硬门槛

不得在生产库上运行测试或 benchmark，不得执行 `db:reset`，不得删除新增表来回滚。发布候选必须满足以下条件：

1. `server/src/schema.sql` 中以 `-- IdeaHub sample library, stage 4 (contract v2).` 开始的区块与 `scripts/migrations/20260829-sample-library-stage4.sql` 字节一致。
2. `node scripts/test-sample-library-stage4.mjs` 通过。
3. 在独立 PostgreSQL 16 与 17 数据库分别设置 `TEST_DATABASE_URL` 后，`node scripts/test-sample-library-stage4-db.mjs` 通过。脚本会拒绝与 `DATABASE_URL` 相同的地址，并只使用随机自有 schema。
4. PostgreSQL 16 生产匹配环境执行 `node scripts/benchmark-sample-library-stage4.mjs`，100 个查询全部满足 2 秒 statement timeout，LSH 索引、召回、短名单、响应大小与 RSS 硬门槛通过。时间 p50/p95 只记录环境，不作为跨硬件门槛。
5. Stage 1–3 与 Collector 回归通过。不得把当前失效的旧 UI 基准误报为通过。

## 备份与核对

在 VPS 当前代码工作区干净、邻居服务正常后，先做同一时间点的三份新备份：

- PostgreSQL 数据库备份。
- `data/uploads` 备份。
- 仓库外样本媒体持久目录备份。

以下命令必须在 VPS 维护者确认实际容器名、数据库用户和两个持久目录后执行。`BACKUP_DIR` 必须是本次发布新建的空目录；示例不会覆盖历史备份：

```bash
set -euo pipefail
BACKUP_DIR="/opt/ideahub-backups/stage4-$(date -u +%Y%m%dT%H%M%SZ)"
UPLOADS_DIR="/opt/ideahub/data/uploads"
SAMPLE_MEDIA_DIR="/opt/ideahub-sample-media"
mkdir -m 700 "$BACKUP_DIR"

docker compose exec -T db pg_dump -Fc -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  > "$BACKUP_DIR/ideahub.dump"
tar -C "$(dirname "$UPLOADS_DIR")" -czf "$BACKUP_DIR/uploads.tar.gz" "$(basename "$UPLOADS_DIR")"
tar -C "$(dirname "$SAMPLE_MEDIA_DIR")" -czf "$BACKUP_DIR/sample-media.tar.gz" "$(basename "$SAMPLE_MEDIA_DIR")"
sha256sum "$BACKUP_DIR/ideahub.dump" "$BACKUP_DIR/uploads.tar.gz" \
  "$BACKUP_DIR/sample-media.tar.gz" | tee "$BACKUP_DIR/SHA256SUMS"
sha256sum -c "$BACKUP_DIR/SHA256SUMS"
docker compose exec -T db pg_restore -l < "$BACKUP_DIR/ideahub.dump" > "$BACKUP_DIR/restore.list"
test -s "$BACKUP_DIR/restore.list"
tar -tzf "$BACKUP_DIR/uploads.tar.gz" >/dev/null
tar -tzf "$BACKUP_DIR/sample-media.tar.gz" >/dev/null
```

数据库备份还必须做一次隔离恢复验证。维护者为 `RESTORE_DB` 选择一次性数据库名，验证完成后删除；不得把生产库作为恢复目标：

```bash
set -euo pipefail
RESTORE_DB="ideahub_stage4_restore_check_$(date -u +%H%M%S)"
docker compose exec -T db createdb -U "$POSTGRES_USER" "$RESTORE_DB"
docker compose exec -T db pg_restore -U "$POSTGRES_USER" -d "$RESTORE_DB" \
  --exit-on-error --no-owner --no-privileges < "$BACKUP_DIR/ideahub.dump"
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$RESTORE_DB" \
  -c "SELECT count(*) FROM samples" \
  -c "SELECT count(*) FROM sample_analysis_versions" \
  -c "SELECT count(*) FROM content_components"
docker compose exec -T db dropdb -U "$POSTGRES_USER" "$RESTORE_DB"
```

恢复验证的三项行数需与迁移前记录一致。若验证失败，停止发布并先修复备份链路。

记录候选提交、迁移文件 SHA-256、PostgreSQL 主版本与备份时间。迁移前记录 Stage 1–3 核心表行数、current 分析 ID 和 JSON 语义摘要。建议至少覆盖 `samples`、`sample_captures`、`sample_analysis_versions`、`sample_analysis_elements`、`sample_comparisons`、`content_components` 与 `content_component_selections`。

本次交付的 Stage 4 迁移 SHA-256 为 `52be36df027e29c987c9a6592236fba3ad5fada05818a9b4fa004df37e145601`。若候选提交后迁移文件继续变化，必须重新计算并以候选中的实际摘要替换此值，同时重跑 PG16/PG17 双执行与 benchmark，不能沿用旧验收结果。

## 数据库优先发布顺序

1. 再次确认数据库、uploads、样本媒体备份均可读。
2. 确认迁移 SHA 与已验收候选一致。
3. 对现有库执行一次迁移，再原样执行第二次。第二次必须成功。
4. 对比迁移前后的 Stage 1–3 行数、current ID 和 JSON 语义摘要；旧数据不得变化。
5. 检查 21 张 Stage 4 表、命名约束、不可变触发器和 10 个以上 LSH band 索引。
6. 重建 IdeaHub 应用容器，确认 `/api/health` 正常。
7. 以管理员调用 `POST /api/sample-retrieval/reindex`，每次请求带唯一 `Idempotency-Key`。轮询 build 详情，必须达到全部 eligible 均为 succeeded 或明确 excluded，failed 为 0，之后才允许新的算法 selection 成为当前版本。
8. 以管理员创建一次聚类任务并等到 succeeded；读取聚类详情，确认每个冻结输入恰好属于一个簇或一个 outlier，且 `stale=false`。
9. 以 reviewer/admin 创建一个仅使用合成安全样本的小型洞察运行。必须明确单一平台、发布时间范围、观察窗口、目标与代理指标确认。检查统计结果包含 n、覆盖率、可靠性和非因果限制。
10. 验证检索、相似、聚类和洞察四组 API，再检查 1440 与 390 页面。
11. 复查邻居服务未受影响，再通知用户切换完成和实际停机时长。

迁移执行示例由维护者将占位符替换为实际容器和数据库名；不要把口令写进命令历史或文档：

## 只读验证查询

```sql
SELECT count(*) AS stage4_tables
FROM pg_tables
WHERE schemaname='public' AND (
  tablename LIKE 'sample_retrieval_%' OR
  tablename LIKE 'component_retrieval_%' OR
  tablename LIKE 'sample_cluster_%' OR
  tablename LIKE 'sample_insight_%' OR
  tablename='sample_element_tag_observations'
);

SELECT indexname
FROM pg_indexes
WHERE schemaname='public' AND indexname LIKE '%retrieval_vectors_band%'
ORDER BY indexname;

SELECT id,status,eligible_count,succeeded_count,excluded_count,failed_count,error_code
FROM sample_retrieval_builds ORDER BY id DESC LIMIT 5;

SELECT id,algorithm_id,build_id,reason,created_at
FROM sample_retrieval_algorithm_selections ORDER BY id DESC LIMIT 5;

SELECT count(*) FILTER (WHERE dirty) AS dirty,
       count(*) FILTER (WHERE last_profile_id IS NULL) AS missing,
       count(*) FILTER (WHERE last_error_code IS NOT NULL) AS failed,
       count(*) AS total
FROM sample_retrieval_states;
```

首个 reindex 完成前，检索和相似接口返回 `409 INDEX_NOT_READY` 是预期行为，不能绕过为旧数据或同步写入。在线检索连接使用 2 秒 statement timeout；reindex、cluster、insight 后台任务不使用该在线超时，但三者共享一个全局 advisory lock，同一时刻只允许一个重任务。

## 回滚

应用故障时回滚应用提交并重建容器，保留 Stage 4 表、profiles、runs 和审计选择记录。Stage 3 应用不会读取这些加法式表。

算法或聚类结果回滚通过新增一条 append-only selection 指向已完成的旧 build/run 完成，禁止修改或删除已有 selection。数据库恢复只用于确认数据库本身损坏的灾难场景，并且必须与同一时间点的 uploads 和样本媒体备份配对恢复。

数据库迁移不会随代码发布自动生效。VPS 仍有“备份、手工执行 SQL 两次、核验、重建、全量 reindex、聚类与洞察 smoke”这些人工步骤。
